# 统一更新日志设计

## 目标

为 aIdea 增加设置页“更新日志”入口，并让应用内更新提示、Gitee Release 正文和 updater 清单使用同一套版本文案。发布流程必须阻止没有更新日志的版本被发布。

## 单一来源

新增 `shell-frontend/src/data/changelog.json`，按版本倒序保存日志：

```json
[
  {
    "version": "0.1.9",
    "notes": "- 修复……\n- 优化……"
  }
]
```

`version` 必须是 `X.Y.Z`，每个版本只能出现一次，`notes` 去除首尾空白后不得为空。日志正文使用纯文本和换行，不引入 Markdown 渲染依赖；Gitee 可直接按 Markdown 显示，应用内使用保留换行的文本展示。

应用前端直接导入该 JSON，发布脚本和补传脚本读取同一文件。这样历史日志随应用安装包固化，不依赖 Gitee 网络，也不会因线上文件变化导致旧版展示内容改变。

## 设置页

在现有“关于”分类上方增加“更新日志”分类和页面。页面按 JSON 顺序展示版本与正文，适配浅色、深色主题，并提供空状态。现有“关于”页的版本信息和检查更新行为保持不变；检查到新版本时的 `update.body` 也来自同一版本日志。

## 发布流程

`release.sh` 在确定目标版本后读取日志文件并校验：目标版本存在、格式正确、无重复版本且正文非空。发布清单的 `notes` 和 Gitee Release 的 `body` 均使用该正文，不再生成 `Release vX.Y.Z` 作为正文。发布后通过 Gitee API 和线上 Raw `latest.json` 校验正文与来源一致。

`resume-release.sh` 使用相同的读取和校验逻辑，禁止补传时回退为占位文案。日志文件加入发布提交，确保 tag 对应的源码包含该版本说明。

## 历史日志

补齐 `v0.1.0` 至当前版本的条目。仅依据提交记录和已知功能整理；无法确认的细节使用概括性表述，不编造具体用户影响。已发布版本不回写 Gitee Release，避免线上历史与当时发布内容不一致；新流程从下一次发布开始强制执行。

## 验证

- 前端测试覆盖更新日志页面的版本顺序、正文和空状态。
- 发布 Skill 的版本同步测试覆盖日志文件存在、目标版本缺失和正文生成路径。
- 修改后执行 `git diff --check`，并按仓库约定运行前端 lint、test、build 及 Rust tests。

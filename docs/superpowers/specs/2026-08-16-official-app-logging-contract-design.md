# 子应用日志规范与接入设计

## 状态

待审阅。本文记录已确认的方向，审阅通过后再同步到 `docs/guide/` 并实施代码接入。

## 背景

aIdea 壳已经统一负责日志级别、保存时间、总容量、生命周期日志和官方应用 stdout/stderr
采集。当前官方应用主要只有启动输出，业务失败、外部请求异常和官方应用前端未处理异常不能
稳定进入统一调试页；内置应用虽然有壳级未处理前端异常捕获，但业务 `catch` 不会自动留下证据。

日志的目标不是记录所有操作，而是在用户提交问题时提供可复制、可定位的最小证据。

## 目标

- 内置应用和官方应用使用同一套级别、格式、脱敏和打点边界。
- 官方应用的服务端日志通过 stdout/stderr 进入壳的统一日志目录和调试页。
- 官方应用前端的未处理异常能够通过应用自己的服务转发到同一运行日志。
- 启动、数据库、外部请求、核心业务和退出异常等关键故障具备证据。
- 子应用 `AGENTS.md` 能长期约束开发行为，但不复制完整平台规范。

## 非目标

- 不做跨仓库公共 Rust crate 或 npm 日志 SDK。
- 不让子应用维护第二套日志文件、上传服务或诊断包。
- 不记录普通点击、完整请求/响应正文或业务数据。
- 不改变壳现有的日志查看页面、保留策略和清理机制。

## 方案

### 1. 权责边界

| 范围 | 负责方 |
| --- | --- |
| 启动、安装、更新、停止、端口、健康检查、进程退出 | aIdea 壳 |
| 数据库初始化和迁移、业务网络请求、同步、AI 网关调用 | 子应用服务端 |
| 页面未处理异常、页面关键请求失败 | 子应用前端；通过应用服务转发 |
| 时间、来源、保存、级别过滤、滚动和清理 | aIdea 壳 |

壳继续采集官方应用 stdout/stderr。子应用第一阶段不直接写 `AIDEA_APP_LOG_DIR`，避免
运行日志出现两份格式不同的记录。`AIDEA_APP_LOG_DIR` 仍保留给平台契约使用。

### 2. 输出格式

子应用每行输出一条日志，首个字段必须是 `DEBUG`、`INFO`、`WARN` 或 `ERROR`：

```text
INFO sync_started account_count=2
WARN sync_retry provider=imap attempt=2 reason=timeout
ERROR sync_failed provider=imap status=403 reason=forbidden
DEBUG request_finished endpoint=/api/projects elapsed_ms=42
```

- 日志消息使用稳定事件名加有限的 `key=value` 上下文。
- 子应用不必自行添加时间戳；壳会追加 `YYYY-MM-DD HH:MM:SS`、来源和通道。
- 一条事件尽量保持单行。换行、堆栈和异常文本必须压缩或转义，不能导致日志结构失控。
- 未识别的输出仍按壳的现有规则处理，默认视为 `INFO`；这只是兼容兜底，不是新代码标准。

### 3. 级别语义

应用读取壳注入的 `AIDEA_LOG_LEVEL`，缺省值为 `info`。壳仍做最终级别过滤。

| 级别 | 含义 | 示例 |
| --- | --- | --- |
| `DEBUG` | 仅调试档需要的详细过程 | 请求耗时、重试判断、解析分支 |
| `INFO` | 标准运行事实和成功/失败结果 | 启动就绪、同步完成、迁移完成 |
| `WARN` | 已处理但值得排查的问题 | 重试、降级、单个账户同步失败 |
| `ERROR` | 当前操作或服务无法完成 | 端口绑定失败、迁移失败、最终请求失败 |

失败只在边界记录一次。底层函数添加上下文后继续返回错误，上层负责记录最终结果，避免同一
错误在每层重复输出。

### 4. 必须打点的事件

每个子应用至少覆盖：

- 启动：资源检查、数据目录、数据库/迁移、端口绑定、服务就绪和启动失败。
- 退出：收到停止信号、正常退出和异常退出。
- 外部依赖：HTTP 401/403/5xx、超时、连接失败、解析失败、重试和最终失败。
- 核心业务：同步开始/完成/失败、AI 网关调用失败、关键数据库读写和迁移失败。
- 前端：未处理 `error`、未处理 Promise rejection、关键请求失败。

不要求记录普通页面点击、列表查询成功、每一条邮件或完整业务正文。

### 5. 敏感信息

任何级别都禁止记录密码、授权码、OAuth 令牌、API Key、邮件正文、通知正文、完整 URL 查询
参数、完整 Diff 和完整响应体。日志字段应使用应用 ID、账户内部 ID、服务商名、HTTP 状态码、
错误类别、重试次数和耗时等可定位但不含秘密的上下文。

### 6. 官方应用前端转发

官方应用前端不能使用 Tauri IPC，也不会自动接入壳的浏览器异常捕获。每个官方应用增加一个
应用内受限日志接口，前端日志模块只发送：级别、来源、稳定事件名、脱敏后的消息和有限上下文；
服务端校验字段长度和级别后，按统一格式输出 stdout/stderr。该接口只监听本机应用端口，不新增
跨应用协议或壳能力。

前端日志转发失败不能阻塞业务，也不能在失败重试中形成日志风暴。

### 7. 封装策略

当前只在各应用仓库内增加最小 `logging` 模块：

- 解析 `AIDEA_LOG_LEVEL`；
- 提供 `debug/info/warn/error` 四个简单入口；
- 统一前缀、单行输出和字段脱敏边界；
- 提供前端异常转发的最小封装。

不抽公共 SDK。等至少三个应用出现稳定且重复的实现，并且维护成本已经高于发布耦合成本时，
再单独评估公共包。

## 验收

- `AIDEA_LOG_LEVEL=warn` 时只保留 WARN/ERROR；`info` 保留 INFO 及以上；`debug` 保留全部。
- 启动失败、端口占用、数据库迁移失败、403、超时、重试和正常停止均能在统一调试页复制到证据。
- 官方应用前端制造未处理异常后，运行日志出现对应脱敏事件。
- 日志中不存在凭据、邮件正文、通知正文和完整响应内容。
- 前端转发接口输入过长、级别非法或消息含敏感字段时不会写入原文，也不会阻塞业务。
- 运行现有应用测试、Lint、构建和 Rust 测试；文档修改执行 `git diff --check`。

## 已知取舍

统一 stdout/stderr 能最快接入现有壳采集，但无法保证第三方日志库的字段都被结构化解析；因此本
阶段只约束首字段级别和单行文本。若后续需要机器检索，再另行设计 JSON 事件格式，不在本次范围内。

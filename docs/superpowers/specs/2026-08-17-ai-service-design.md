# AI Service 分层与审计设计

## 状态

本规格记录已确认的 AI Service 设计。它用于进入实施计划，正式实现完成后仍以 `docs/guide/aidea-ai-service.md` 为长期契约。

已确认：

- AI Service 的内部应用 ID 是 `ai-service`。
- 官方应用通过 `AIDEA_AI_SERVICE_URL` 和 `AIDEA_AI_SERVICE_TOKEN` 调用 AI Service。
- AI Service 保存多个模型配置，用户可以拖拽调整顺序；服务可绑定指定模型，未绑定时使用排序第一的可用模型。
- 首期不为不同子应用区分独立 token；审计页首期不承诺可靠显示来源应用。
- 子应用只负责发送 `message` 和解析自己的业务结果，不传模型、API Key、工作目录、工具列表或模型参数。
- 首期使用 Rig 和六个内部工具：`read_file`、`write_file`、`edit_file`、`exec`、`search`、`list_dir`。

## 目标

1. 让 Agent、图片、视频和流式能力可以按协议和参数独立演进。
2. 让 AI Service UI 能展示当前真正提供的服务。
3. 让用户查看一次 AI 调用的模型轮次、工具调用、耗时和提供方返回的 token 用量。
4. 不把业务应用名称、业务流程或安全策略放进公共接口。

## 非目标

- 不实现第三方插件市场、运行时服务发现或远程多租户服务。
- 不为 Worktrace、Mail Center 等业务应用分别创建 endpoint。
- 不在本期实现图片、视频或 SSE；只预留它们按服务独立增加的路径。
- 不保存完整提示词、完整邮件正文、完整代码 diff、完整工具输出或上游 API Key。

## 接口分层

AI Service 使用 `/api` 作为本机服务命名空间，当前 Agent 接口为：

```http
POST /api/agent
Authorization: Bearer <AIDEA_AI_SERVICE_TOKEN>
Content-Type: application/json
```

请求体保持最小形式：

```json
{
  "message": "读取 /Users/fourli/xxx-project 的代码变更，生成符合 Conventional Commits 规范的 commit message"
}
```

Agent 成功响应保持现有契约：

```json
{
  "code": 0,
  "data": "feat(order): 完成订单对接功能 #1001"
}
```

`/api` 不再作为 Agent 的兼容别名。当前没有正式子应用消费者，因此直接采用 `/api/agent`，避免两条入口长期分叉。

后续能力按能力族增加独立路径：

| 能力 | 路径 | 本期状态 |
| --- | --- | --- |
| Agent 一次性非流式任务 | `POST /api/agent` | 本期实现 |
| Agent 流式任务 | `POST /api/agent/stream` | 需要时新增 SSE 契约 |
| 图片生成 | `POST /api/image-gen` | 真实需求出现后新增 |
| 视频生成 | `POST /api/video-gen` | 真实需求出现后新增，允许独立定义异步响应 |

一次性、流式、图片和视频的请求参数与成功响应可以不同。它们共享认证、基础 HTTP 错误处理和审计入口，但不强行共享业务 `data` 结构。`/v1/responses`、`/v1/chat/completions` 仍然只属于 AI Service 的上游适配。

## 模型配置

模型配置是 AI Service 自己维护的列表，每项包含提供方、Base URL、API Key、模型名和稳定配置 ID。API Key 只保存于 `app-data/ai-service/app.db`，不进入子应用请求或 `exec` 环境。

配置页面支持新增、编辑、删除和拖拽排序。排序字段决定全局默认模型：服务未绑定具体模型时，使用排序第一的可用配置。

服务注册表可以保存一个可选的 `model_id`。绑定后，该服务固定使用对应配置；未绑定时按上述默认规则选择。绑定的配置被删除或不可用时，服务显示未配置并拒绝新请求，不静默改用其他模型，避免模型变化造成不可预期的业务结果。

## 内部服务注册表

服务列表是 AI Service 的内部注册表，不是子应用运行时发现协议。每项至少包含：

- 稳定的服务 ID，例如 `agent`。
- 对外路径和协议类型，例如同步 JSON 或 SSE。
- 面向用户的名称和说明。
- 当前启用状态。
- 内部执行配置的引用，例如 Agent 工具集合和超时策略。
- 可选的模型配置 ID；未设置时使用模型列表排序第一的可用配置。

首期注册表只列出 `agent`。图片、视频和 SSE 真正实现后再加入列表，不展示未实现的占位服务。

服务 ID 可以选择内部工具、超时和授权策略，但这些字段不出现在子应用请求中。业务应用仍通过 `/api/agent` 搭配自己的 `message` 完成不同任务。

AI Service 页面提供：

1. 模型配置。
2. 服务列表。
3. 模型测试，包括普通模型调用和 Agent 任务。
4. 审计记录。

模型配置页的模型列表支持拖拽排序；服务列表中可以为每个服务选择“跟随默认”或某个已配置模型。

## 审计记录

审计记录与 aIdea 普通运行日志分开，保存于 `app-data/ai-service/app.db`。一次调用产生一个 run，Agent 的模型轮次、工具调用、授权等待和最终结果产生有序 event。

run 记录以下元数据：

- 服务 ID。
- 当前状态：成功、失败、超时、取消或用户拒绝。
- 开始时间、结束时间和总耗时。
- Agent loop 次数。
- 提供方返回的 input、output、total token；未返回时显示“未提供”。
- 脱敏后的错误摘要。

event 记录以下元数据：

- 顺序号和事件类型：模型轮次、工具调用、授权、结果。
- 事件名称和耗时。
- 当前轮次提供方返回的 token 增量（如果有）。
- 可展示的短摘要。

审计日志提供全局开关，默认开启。关闭后只停止新调用的审计记录，不删除历史数据；已开始的调用按照开始时的开关状态完成记录。审计页在关闭状态显示明确提示，历史记录仍可查看。

AI Service 使用统一的 `AuditRecorder` 打点入口包裹请求开始、模型轮次、工具调用、授权等待和请求结束。关闭时先走无操作快路径：只读取一个内存中的开关，不创建数据库连接、不格式化摘要、不复制提示词或工具结果，也不向后台写入事件。打点失败只记录 AI Service 自身的脱敏告警，不得改变模型请求结果。

审计页展示调用列表和单次详情时间线。时间统计使用单调时钟计算，区分总耗时、模型耗时、工具耗时和授权等待耗时。图片或视频服务的非 token 用量由对应服务以自己的摘要字段记录，不能假设所有模型都按 token 计费。

审计默认不保存完整 `message`、模型原文、邮件正文、完整 diff、完整命令输出或凭据。工具摘要需要做长度限制和常见凭据脱敏。首期不提供公开的审计查询 HTTP 接口，也不提供任务管理 API；审计页通过内置应用 IPC 读取 AI Service 自己的数据库和当前进程内事件。

首期不区分子应用 token，因此审计记录不保证显示可靠的调用来源。以后如果确实需要来源统计，再增加由 aIdea 管理的每应用 token 映射，不改变请求体。

## 运行与安全

`agent` 服务继续使用 Rig 执行 Agent 循环，注册六个本机工具。普通 git、curl、构建和测试默认允许；高破坏力命令经过 AI Service UI 授权；明确危险的系统命令直接拒绝。服务路由可以绑定不同的内部工具集合，但不把权限 DSL 暴露给子应用。

AI Service 仍是用户权限级可信自动化，不是强隔离沙箱。API Key 和 AI Service token 不进入 `exec` 子进程环境。外部邮件、Redmine 内容和代码注释按不可信引用内容处理。

## 迁移与验证

- 当前没有正式子应用消费者，因此实现时直接注册 `/api/agent`，删除旧 `/api` Agent 路由。
- 更新开发手册、官方应用契约和内置应用目录中的路径引用。
- 为服务注册表、Agent 路由、审计 run/event、token usage 缺失和超时路径补充 Rust 测试。
- 为多模型排序、服务模型绑定、绑定模型删除后的失败路径、审计开关无操作快路径补充 Rust 测试。
- 前端测试覆盖服务列表、审计列表/详情、模型测试入口和高风险授权弹窗。
- 只运行同步 JSON Agent；图片、视频、SSE 在各自需求确认后单独设计和测试。
